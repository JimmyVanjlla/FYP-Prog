# AI-Based Restaurant Resource Management and Order Demand Prediction System

Implementation of Ng Jim Shen's Final Year Project (see `../` for the FYP1
report: Chapters 1-4). Built module-by-module following the sprint order in
Form 2's project schedule. Current status: **Sprint 2 — Module 3 (Inventory
Management), Module 4 (Demand Forecasting), Module 5 (Kitchen
Operations)**.

## Stack

- **Backend**: FastAPI + SQLAlchemy + Alembic, Python 3.11, JWT auth, Postgres (Supabase)
- **Frontend**: Flutter (Dart), targeting Android/iOS
- **Background jobs** (from Sprint 2 onward): Celery + Redis, Facebook Prophet, ReportLab

## Backend setup

```bash
cd backend
py -m venv .venv
./.venv/Scripts/pip install -r requirements.txt   # Windows
# source .venv/bin/activate && pip install -r requirements.txt   # macOS/Linux

cp .env.example .env
# Fill in DATABASE_URL (Supabase Postgres connection string) and JWT_SECRET.
# See the comments in .env.example for exactly where to find each value.

./.venv/Scripts/python -m alembic upgrade head
./.venv/Scripts/python -m uvicorn app.main:app --reload
```

**Windows only — one-time Prophet setup** (not needed on the Linux deployment target):
```bash
py -m cmdstanpy.install_cxx_toolchain --silent   # via .venv python; installs a minimal RTools/MinGW
# open a NEW terminal window here so it picks up the PATH change, then:
./.venv/Scripts/python -c "import cmdstanpy; cmdstanpy.install_cmdstan()"   # takes several minutes
./.venv/Scripts/python scripts/setup_windows_prophet.py   # fixes a broken stub in prophet's Windows wheel
```
See `scripts/setup_windows_prophet.py`'s docstring for why that last step is needed.

API docs (auto-generated by FastAPI): http://127.0.0.1:8000/docs

Run tests:

```bash
./.venv/Scripts/python -m pytest
```

## Frontend setup

```bash
cd frontend
flutter pub get
flutter run --dart-define=API_BASE_URL=http://127.0.0.1:8000
```

`API_BASE_URL` defaults to `http://10.0.2.2:8000` (the Android emulator's
alias for the host machine), which is right for the Android emulator but
wrong for a physical device, iOS simulator, or `flutter run -d chrome` —
override it explicitly for those.

Run tests: `flutter test`. Run static analysis: `flutter analyze`.

## What's implemented so far

**Sprint 1**
- **Module 1**: registration, login (JWT), role-based access control,
  Manager staff management (activate/deactivate/reassign role), audit log.
- **Module 2**: menu item CRUD (Manager-only), recipe-to-ingredient links,
  validation on price/quantity, stock-based availability (wired up in
  Sprint 2 once Module 3 existed). Profit margin calculation is still
  stubbed — pending SupplierPricing (Module 9, Sprint 4).

**Sprint 2**
- **Module 3**: ingredient CRUD, low-stock threshold (system default +
  per-ingredient override), manual stock adjustments, stock batch receipt,
  Kitchen→Inventory restocking requests, near-expiry batch scanning
  (Celery Beat, daily).
- **Module 4**: Order intake, Prophet-based demand forecasting per
  (menu item, meal period) — trained daily via Celery Beat, skips items
  with insufficient history, backfills forecast accuracy against real
  orders once the forecast date has passed.
- **Module 5**: prep recommendations derived from forecasts, Kitchen Staff
  confirm/adjust (justification required beyond the configured deviation
  %), end-of-service leftover logging, push notifications (stored
  honestly as `queued_for_retry` until a real FCM service account is
  configured — see `app/services/notifications.py`).
- Celery + Redis are live (`app/celery_app.py`); Prophet needed a one-time
  Windows toolchain fix — see the Prophet setup section above and
  `app/core/windows_toolchain.py`.

See `backend/app/` (routers → services → models, one file per module) and
`frontend/lib/features/` for the code, and each file's module-level
docstring/comment for which FR(s) it implements.
