# AI-Based Restaurant Resource Management and Order Demand Prediction System

Implementation of Ng Jim Shen's Final Year Project (see `../` for the FYP1
report: Chapters 1-4). Built module-by-module following the sprint order in
Form 2's project schedule. Current status: **all 5 sprints (11 modules)
built, plus a full audit pass against the report's use-case tables
(`AUDIT_CHECKLIST.md`) — every actionable gap found there is now fixed.**

## Stack

- **Backend**: FastAPI + SQLAlchemy + Alembic, Python 3.11, JWT auth, Postgres (Supabase)
- **Frontend**: Flutter (Dart), targeting Android/iOS
- **Background jobs** (from Sprint 2 onward): Celery + Redis, Facebook Prophet, ReportLab

## Backend setup

```bash
cd backend
py -m venv .venv
./.venv/Scripts/pip install -r requirements.txt   # Windows
# source .venv/bin/activate && pip install -r requirements.txt   # macOS/Linux

cp .env.example .env
# Fill in DATABASE_URL (Supabase Postgres connection string) and JWT_SECRET.
# See the comments in .env.example for exactly where to find each value.

./.venv/Scripts/python -m alembic upgrade head
./.venv/Scripts/python -m uvicorn app.main:app --reload
```

**Windows only — one-time Prophet setup** (not needed on the Linux deployment target):
```bash
py -m cmdstanpy.install_cxx_toolchain --silent   # via .venv python; installs a minimal RTools/MinGW
# open a NEW terminal window here so it picks up the PATH change, then:
./.venv/Scripts/python -c "import cmdstanpy; cmdstanpy.install_cmdstan()"   # takes several minutes
./.venv/Scripts/python scripts/setup_windows_prophet.py   # fixes a broken stub in prophet's Windows wheel
```
See `scripts/setup_windows_prophet.py`'s docstring for why that last step is needed.

API docs (auto-generated by FastAPI): http://127.0.0.1:8000/docs

Run tests:

```bash
./.venv/Scripts/python -m pytest
```

## Frontend setup

```bash
cd frontend
flutter pub get
flutter run --dart-define=API_BASE_URL=http://127.0.0.1:8000
```

`API_BASE_URL` defaults to `http://10.0.2.2:8000` (the Android emulator's
alias for the host machine), which is right for the Android emulator but
wrong for a physical device, iOS simulator, or `flutter run -d chrome` —
override it explicitly for those.

Run tests: `flutter test`. Run static analysis: `flutter analyze`.

## Post-Sprint-5 fix: FR4.5

A full FR-by-FR audit against the report turned up one real gap: FR4.5
("incorporate leftover feedback data to refine Prophet forecast outputs
downward for persistently over-forecasted dishes") was never actually
implemented — an earlier comment claimed the next Prophet training cycle
would "naturally" reflect Module 7's portion-size reductions, but that's
wrong: `quantity_per_serving` only affects ingredient consumption per
order, not the order *count* Prophet trains on. Fixed by applying a
direct downward scale to `predicted_quantity` in
`app/services/forecasting.py::_leftover_adjustment_factor`, reusing
Module 7's exact `leftover_rate` signal — see that function's docstring,
and `test_high_leftover_rate_pulls_forecast_down` in
`tests/test_forecasting.py` for the regression test. 61/61 tests passing.

## Post-Sprint-5 fixes: broader NFR/architecture audit

Asked "does everything else match the docs" — beyond the FR-level check
above, this turned up two more real gaps, both now fixed:

- **Waste aggregation wasn't actually scheduled.** Ch4 §4.1 lists "waste
  aggregation" as one of Celery Beat's five scheduled jobs, but

## Post-Sprint-5 fix: the "configurable" thresholds weren't configurable

Kept auditing ("anymore?") and found the biggest gap yet: `SystemConfig`
(default low-stock threshold, leftover-rate threshold, prep-deviation
threshold, portions-per-staff ratio, near-expiry window) was **read-only
everywhere** — every module reads it via `get_or_create_config()`, but
nothing could ever write to it. This directly contradicts two explicit
FRs (FR3.3, FR7.5) and Ch3's own Restaurant Manager use-case list, which
names "configure system settings" outright. Fixed: `GET`/`PATCH /config`
(read by anyone, write Manager-only), with FR7.5's 0-100% validation on
`leftover_rate_threshold` and a test proving a config change actually
changes downstream behavior (not just sits in the database unused).
71/71 tests passing.

## Post-Sprint-5 fix: 10 missing read endpoints (write-only data)

One more audit pass turned up a systemic pattern, not isolated bugs: for
several entities, I'd built the mutation endpoint each FR names ("allow X
to create/confirm/set...") but never the corresponding read endpoint,
leaving the data write-only. The worst of these was an actual functional
blocker — `DeliveryItem` had no GET at all, meaning Delivery/Logistics
Staff had no way to discover what `item_id`s or expected quantities even
existed before calling `confirm-receipt` (FR10.2). Fixed all 10:

- `GET /deliveries/{id}/items` (the blocker above)
- `GET /procurement/suppliers/pricing`, `GET /procurement/budget`
- `GET /staffing/schedules/{id}/recommendations`, `GET
  /staffing/schedules/{id}/assignments`
- `GET /kitchen/prep-recommendations`
- `GET /inventory/stock-batches`, `GET /inventory/stock-adjustments`
- `GET /forecasting/orders`, `GET /forecasting/accuracy`

## Post-checklist hardening pass: production-readiness gaps

A different kind of audit than the ones above — not "does it match the
report" but "what would a real deployment need that the report doesn't
necessarily call out." Found and fixed:

- **No pagination on almost any list endpoint.** `GET /forecasting/orders`,
  `/inventory/ingredients`, `/procurement/purchase-orders`, `/deliveries`,
  etc. all returned entire tables unbounded. Every list endpoint across
  all 9 routers now takes `limit`/`offset` (capped at 500 per page).
- **Open self-registration to any role, including Manager/Owner.**
  `/auth/register` let anyone grant themselves manager-level access with
  no authorization check — a deliberate Sprint 1 stopgap that was still
  live. Now: self-registering as Restaurant Owner/Manager is only allowed
  once (the system's bootstrap window); beyond that, an existing Manager
  provisions further Manager/Owner accounts via the new `POST /users`.
- **No startup check on `JWT_SECRET`.** It defaulted to a literal string
  baked into this public repo's source. `Settings` now refuses to
  construct if `ENVIRONMENT=production` and the secret is still that
  default — fails loudly at startup instead of silently running forgeable.
- **No rate limiting on `/auth/login`.** Unlimited password attempts, no
  backoff. Now rate-limited per email via a Redis fixed-window counter
  (`app/core/rate_limit.py`, configurable via `LOGIN_RATE_LIMIT_*`), with
  a fail-open design so a down Redis never takes login down with it.
- **No centralized logging or error monitoring at the API layer.** Celery
  tasks logged; routes didn't. Added `app/core/logging_config.py` plus a
  global unhandled-exception handler in `main.py` that logs the full
  traceback server-side before returning a generic message to the client.
- **CORS was simply undecided** — no `CORSMiddleware` at all. Now
  explicit: empty-by-default (safe, doesn't affect the Flutter mobile
  app), configurable via `CORS_ALLOWED_ORIGINS` for a future web target.
- **Bonus bug found while re-seeding dev data**: `_waste_data`/
  `_budget_data` in `app/services/reporting.py` compared a timezone-aware
  `datetime` column against a bare `date` upper bound, which Postgres
  casts to midnight-start-of-day — silently excluding anything logged
  *later that same day*. A weekly report generated "through today" was
  quietly missing today's own waste/spend. Fixed via `_end_of_day()`.

All 6 hardening items plus the reporting fix are covered by new tests
(`tests/test_app_settings.py`, `tests/test_pagination.py`, new cases in
`tests/test_auth.py` and `tests/test_reporting.py`).

A one-time dev data seeder lives at `backend/scripts/seed_dev_data.py` —
registers one account per role, a Malaysian-menu set of ingredients/
suppliers/menu items, 8 weeks of order history, 3 weeks of leftover logs,
and runs forecasting/portion-feedback/waste-trend training so the app
isn't staring at empty screens. See its docstring for usage; it's meant
for a single run against a fresh database, not repeated seeding.

## Free-tier cloud gotchas (if you come back after a break)

- **Redis Cloud deletes inactive free databases.** After roughly a month
  of no traffic, the free-tier Redis database is deleted outright (the
  hostname starts returning NXDOMAIN, not just a timeout) — this
  happened once already (2026-10-28), losing the Celery broker/cache
  (no persistent app data lives there, so nothing important was lost).
  Fix: create a new free database in the Redis Cloud dashboard and drop
  its connection string into `backend/.env`'s `REDIS_URL`.
- **Supabase's direct DB host is IPv6-only.** `db.<ref>.supabase.co`
  (the "Direct connection" string) only resolves to an IPv6 address on
  newer projects. If your network/machine has no outbound IPv6 route,
  connections fail with `getaddrinfo failed` even though the project is
  very much alive (confirm with `curl https://<ref>.supabase.co/rest/v1/`
  — a `401` means it's up). Fix: use the **Transaction pooler**
  connection string instead (Supabase dashboard → Connect → Transaction
  pooler, port `6543`, host like
  `aws-0-<region>.pooler.supabase.com`) — same password, just a
  different host/user (`postgres.<project-ref>` instead of `postgres`).
  This is what `backend/.env`'s `DATABASE_URL` uses now; no data was
  lost, this was a connectivity issue only.
